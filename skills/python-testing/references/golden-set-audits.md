# Golden-set audit procedure

## 1. Establish scope and contracts

- Locate fixtures, their builders, test consumers, and documented gate commands. Trace the exact score function rather than inferring its meaning from a field named `confidence`.
- Distinguish public-entry-point goldens from helper-level examples. Inspect nearby supporting tests before claiming a capability is absent repository-wide.
- Build a field-to-assertion matrix: recorded field, labeled case count, comparator, null handling, and actual enforcement. Stored fields are not coverage unless assertions consume them.
- Classify expectations generated by the implementation as characterization snapshots. A target address alone does not independently label every parsed component.

## 2. Measure the actual corpus

Use the repository interpreter and a bounded scratch script with `json`, `collections.Counter`, and `pathlib`. Compute rather than manually tally:

- Total rows, unique IDs, raw duplicates, and duplicates using the existing domain normalizer.
- Category/source distributions and geographic or semantic slices.
- Non-null label coverage, target-bearing rows, negative labels, and missing metadata.
- Cross-suite input overlap and distinct expected entities; many spelling variants of a few entities do not establish broad geographic coverage.
- Differences between documented totals and actual fixture totals.

Label geographic counts derived from parser outputs as baseline classifications, not independently verified geography. Avoid printing raw production records or sensitive contact data.

## 3. Trace selection and refresh

- Identify first-N selection, parser-score thresholds, verification requirements, rejected disagreements, and shared deduplication order. These can create success-conditioned selection bias.
- Distinguish noisy valid inputs from true negatives; a category name does not establish its expected behavior.
- Inspect whether refresh preserves inputs, stable IDs, and reviewed expectations. Positional IDs can silently identify new inputs after reselection.
- Check source identities/hashes, code revision, knowledge-base revision, and label adjudication metadata. Check source availability without rebuilding the corpus.
- Check integrity enforcement for missing/empty fixtures, unique IDs, category membership, and required fields. Minimum mapped-case counts cannot protect unrelated categories from deletion.

## 4. Execute tests and adversarial oracle probes

Run only the relevant tests, typically `python -m pytest -n 4 <golden_test_files> -q`. Keep test counts distinct from corpus row counts when one test loops through a dataset.

Test the assertion layer itself with controlled wrong outputs:

| Probe | Weakness exposed |
| --- | --- |
| Replace street, house number, district, or ward while preserving scores | Semantic fields not asserted |
| Set false verification to true | One-sided boolean contract |
| Add output where explicit null is expected | Null treated as unlabeled |
| Return the entire raw address as the extracted field | Substring checks permit contamination |
| Change numeric suffix while retaining expected text as a prefix | Boundary-insensitive string comparison |
| Use an unknown category/cluster with empty output | Branch chain fails open |

Prefer passing mutated copies into existing assertion helpers. If assertions are embedded in a test, load that test module and temporarily patch only its producer with `unittest.mock.patch` and a minimal fake result. This is an intentional exception to normal no-internal-mocking guidance: the assertion contract is the logic under test. Restore the patch after each probe and do not modify production code or authoritative fixtures.

Report accepted mutant count and denominator. An accepted mutant proves a gate blind spot, not that the production implementation emits that output. Do not call an intentionally incomplete local probe a full production replay.

## 5. Compare outputs without declaring unreviewed regressions

Replay the frozen inputs and compare recorded semantic fields against current outputs. Preserve case IDs and count differences by field; field counts may overlap. Call these differences drift until reviewed. Canonicalization and corrected labels can legitimately change outputs.

Do not automatically assert every old snapshot value: that freezes existing bugs. Review changed values first, then introduce explicit semantic expectations.

## 6. Recommend the smallest useful redesign

Keep separate contracts for:

1. Reviewed semantic correctness, including explicit null/false and accepted alternatives.
2. Characterization or score compatibility on fixed inputs.
3. Representative accuracy evaluation selected independently of current success.
4. Calibration, only when scores are intended as probabilities and independent labels exist.

Require exact normalized extraction where appropriate; encode alternative valid fields explicitly rather than accepting any matching output field. Add negative pairs before interpreting increased similarity scores as better matching. Separate corpus expansion, label adjudication, and snapshot refresh so a single generator cannot erase failures and bless new outputs simultaneously.

## 7. Report

Lead with suitability by purpose, not a single unsupported quality rating. Provide actual inventory, prioritized file-and-line evidence, executed mutation results, sampling/provenance limits, strengths, and an ordered remediation table. State which tests ran and whether repository files changed. Prefer stronger assertions and labels before recommending more cases.
