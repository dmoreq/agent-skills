# Search-ranking evaluation and artifact optimization

Use this recipe when a search benchmark accepts per-target sample sizes but the request is for an *unstratified*, fixed-size random sample from a large event Parquet.

1. **Select source and eligibility.** Inspect source schema, row count, date range, and null queries. Exclude empty search text and unsupported targets using the same eligibility predicate as the evaluator. Verify source dates against every feature store's training cutoff; a different file or disjoint event IDs is not an out-of-time holdout. Before rebuilding an existing click prior, filter each declared training file to a bounded set of evaluation POI IDs, normalize distinct raw queries with the same production function, and aggregate `(normalized query, POI)` clicks per file. Compare those sums with the stored counts for pairs with support in the final training file; matching cumulative counts demonstrate that the final week is already included, even if the documented command omits it. Check the builder's count threshold and POI filter before treating mismatches as missing data. If the store has no metadata and this audit is inconclusive, rebuild from explicit source files or disable it for the holdout; do not rerun a large builder merely because a filename or example command is ambiguous.
2. **Draw the mixed-target sample first.** For a large Parquet, use row-group metadata for total rows, draw a seeded ordered `random.sample(range(total_rows), draw_size)`, and use Arrow row-group `take` to load only selected offsets. Load prior benchmark IDs and exclude them **before** taking the first N eligible events; filtering duplicates after selection breaks the requested sample size. Filter empty queries and unsupported targets in draw order. Oversample enough to cover invalid and excluded rows; if insufficient, extend the draw without replacement rather than reducing N. This preserves a uniform sample from eligible, previously unused events without collecting the whole file. Keep raw records in gitignored scratch, not in reports.
3. **Adapt the runner without changing membership.** For a mixed-target sample, count pickup and dropoff in the preselected N-row Parquet. Pass those exact counts as `--pickup-size` and `--dropoff-size`; the runner may permute within target but cannot change membership. For a target + intent-only sample, route each eligible event with the same query, target, and validated coordinates as production **before** retaining the first N; otherwise the final intent cohort may be smaller or biased. If the report runner assumes both targets are nonempty, reuse its sample preparation, engine construction, execution, and metric functions in a cohort-only harness rather than adding a dummy case or changing shared runtime behavior. Record source, seed, eligibility, counts, and absence of event-ID overlap with earlier evaluations.
4. **Audit the result at case level.** Assert N output rows, N unique IDs, zero search errors, and count `rank == 1` for all target rows. Separately count clicked/labeled rows and any target + intent subset. Cross-check the clicked count and hits in the metrics JSON; evaluator defaults may exclude abandoned searches even when the sample size includes them. For missing targets, check canonical aliases, top-level `poi_id`, and nested `children.poi_id` before declaring them absent from the index; validate status, target visibility, and coordinates separately. Trace target visibility after retrieval, supplementation, dedup/scoring, and final top-10 truncation. A parent/child POI present only in nested data is not a missing index record, and an indexed target beyond top 10 is not a retrieval miss. Before proposing a lower click-prior threshold or wider historical injection, count earlier `(normalized query, selected POI)` support among targets absent from the top results. Partition into zero, below threshold, and at/above threshold, including canonical aliases; use the same key normalization as the store. If filtering source logs by exact raw query for speed, label zero counts as *raw-exact only*: other raw spellings can share the normalized key. A supported target is still only a retrieval opportunity, not a new rank-1 hit. A broader waterfall or fallback must also pass paired Hit@1 and latency checks; more candidates can displace correct results.
5. **Report comparable and non-comparable quantities.** Give both `hits / all cases` and `hits / clicked cases` when unlabeled cases exist. If the contractual denominator includes abandoned searches, keep them in the fixed cohort as misses; never resample clicked-only cases to improve the score. Compute the maximum possible all-case score from the labeled fraction before tuning. Do not compare a focus-intent goal with the all-target percentage. For a different source week, show cohort-to-cohort differences as descriptive only. Check `(normalized query, selected POI)` overlap with click priors and personalized history; report overlap as a limitation, not proof of causal leakage. Only claim a clean temporal holdout when all training stores predate the events.

## Bounded-demotion rank guard

Use this only when a strict paired rank contract justifies running both old and new rankers. It is not a way to repair relevance labels.

1. **Replay both complete orders.** Pin each ranker's source and the same frozen candidate pool. Assert the old arm's captured top-10 IDs, scores, and displayed child IDs before trusting its full ranks; cross-check selected full ranks from independent diagnostics. Confirm the new arm matches its saved selected ranks. A top-10-only capture cannot enforce a full-pool rank bound.
2. **Merge without the selected ID.** Map each displayed POI ID to its *earliest* old row. If any old ID is absent from the new order, return the old complete order. If the new order already meets every old ID's deadline (`old_rank + allowed_demotion`), leave it unchanged; repeated IDs need only one qualifying occurrence. Otherwise assign deadlines to the first new group containing each old ID. At each output slot, keep the earliest remaining new-order group only if sorting the other deadlines shows they fit all remaining slots; otherwise take the earliest-deadline group. Verify every old displayed ID's earliest final rank and fall back to the old order on a conflict. Test both feasible parent/child splits and repeated displayed IDs; a naive 'pick new unless one ID is due now' rule can reject a feasible schedule.
3. **Measure the cost and quality before deployment.** Audit the full comparable cohort, including within-top-10 demotions, old misses beyond top 10, parent/child IDs, all fallback modes, and gains/losses in final Hit@1/10. Time old ranking, new ranking, and the merge separately; process-wall time includes I/O and parallelism and is not request latency. A frozen offline merge proves only that cohort's rank bound; inference requires both pinned rankers and a separate latency and deployment review. Never look up the clicked ID at inference.

## Rank-first feature and artifact experiments

1. **Trace every consumer before changing stored values.** Separate candidate hydration, scoring, fallback lookup, and post-ranking promotion. A score cap does not permit capping stored counts when hydration or promotion still orders by uncapped counts. Preserve ordered candidate membership and tie semantics; introduce deterministic tie-breaking as a separate behavioral change.
2. **Measure physical waste before lossy pruning.** Open SQLite sources through `Path.resolve().as_uri() + '?mode=ro'` with `uri=True`; inspect schemas, `PRAGMA page_count`, `PRAGMA freelist_count`, and aggregate `dbstat` payload/unused bytes where available. Test `VACUUM INTO` on a scratch copy. Zero freelist pages do not mean every live page is densely packed. Report actual file sizes, including new dictionaries, indexes, totals, and hydration structures.
3. **Prove logical redundancy against lookup semantics.** If exact values overwrite per-key fallback values, equal exact/fallback rows can be omitted only when presence itself has no other meaning. Verify threshold behavior, exhaustive effective-value equality, and unchanged fallback tables on copies, then replay final ranks. Keep reconstructible training sources: removing redundant output values can destroy provenance needed by a future model. Do not generalize this deletion rule to query-level fallback or provenance-sensitive consumers.
4. **Compare simple lexical baselines before adding machinery.** Inspect existing token rules, field weighting, analyzer, and retrieval similarity. For short titles, try binary IDF-weighted coverage before TF-IDF cosine. Freeze the IDF corpus outside the final test. Preserve numbers, streets, branch qualifiers, and phrase order; unordered keyword keys can merge different intents. Test token-based click backoff separately from lexical reranking, keep exact lookup first, prevent repeated counting of a multi-token event, and bound postings/fan-out. Count the token map in artifact size.
5. **Define Bayesian and residual semantics explicitly.** Rebuild denominators from uncensored training events when existing stores have already discarded low-count pairs. Noisy-OR over heuristic scores is not automatically a calibrated posterior. For sparse posterior-minus-parent residuals, retain signed values and define absence as zero contribution. Pruning residuals does not generally preserve probability normalization; either export a ranking feature without probability claims or account explicitly for omitted probability mass. Shrinkage does not correct exposure bias without suitable observations and propensity assumptions.
6. **Prune by measured final-rank value.** Start with support/residual/frequency buckets rather than expensive exhaustive row attribution. For each removal, count lost hits, gained hits, winner churn, candidate recall, and actual bytes saved. Compare count-threshold and residual-threshold baselines at matched sizes. A frequency-times-magnitude proxy measures influence, not correctness. A row with no observed rank flip is not universally redundant. Re-evaluate the complete pruned artifact because individually harmless removals can jointly change the winner.
7. **Separate diagnostic replay from end-to-end evidence.** Fixed candidate lists isolate reranking but cannot validate hydration changes. Include retrieval misses in the end-to-end denominator. Validate accelerated replay against the real pipeline before trusting it: tiers, deduplication, score clamping, diversity, and promotion invalidate naive score-margin reasoning. Select compatible finalists on validation, then test their combination once on the untouched later holdout.

## Compression-first use of auxiliary event data

1. **Inspect metadata before scanning large event files.** Use `pyarrow.parquet.ParquetFile(path)` to inspect `schema_arrow`, row counts, row groups, and per-group timestamp/date min/max statistics. Report how many groups have usable statistics; footer ranges establish coverage, not event uniqueness or content validity. Aggregate small derived statistics files before requesting a broad raw-event scan. Keep user identifiers, addresses, and coordinates out of reports.
2. **Separate declared provenance from verified provenance.** Record a user-confirmed mining window as declared evidence, then verify timestamps, timezone boundaries, manifests, and source hashes. A later source window is not automatically untouched: inspect prior evaluation outputs and sampling manifests before reserving it. For development folds inside the mining window, rebuild all derived signals at each earlier cutoff; never reuse the full-window artifact to claim out-of-time performance on its training period.
3. **Audit auxiliary-signal construction before treating it as ground truth.** Trace status filters, requested versus actual endpoints, rounding, joins, deduplication, target separation, and event cutoffs. Rounded-coordinate joins can attribute one endpoint to multiple entities; absent support can mean mapping failure or threshold censoring rather than irrelevance. Do not equate a builder's completed-event description with verified completion status. Do not join search and trip events by user alone when event/session attribution is missing.
4. **Measure residual value against the complete existing baseline.** Check whether auxiliary popularity already affects scoring, tiers, deduplication, or promotion. Compare the existing auxiliary-enabled baseline plus full history against that same baseline plus sparse exceptions. Do not manufacture gains by disabling an existing signal in the control. Evaluate compact per-user/target top-K histories as lossy alternatives because varying candidate pools can make omitted preferences decisive. Never delete history solely for missing auxiliary support.
5. **Test representation and deployment tiers before adding models.** Compare lossless key encoding, compact stores, and compressed snapshots using installed dependencies; prove reversible IDs including leading zeros, aliases, and numeric bounds. Compressed columnar files are not drop-in indexed stores, and loading them into dictionaries can move disk savings into RAM. Ablate no-store, single-store, hydration-only, and compact-history variants to locate the smallest sufficient signal set. Count shared auxiliary payloads once, report marginal and total deployment bytes, and preserve hydration ordering. Archive compression alone does not reduce expanded serving-disk use.
6. **Choose minimum feasible bytes, not the highest-quality point.** Establish quality noninferiority and operational budgets before lossy pruning. Review each isolated experiment independently, including blocked or deferred outcomes. Select the smallest measured artifact meeting those gates; explore additional features only when they can enable further compression. Keep original training sources reconstructible and publish experimental outputs separately from production artifacts.

## Index refresh and catalog hygiene

Use this when asked whether rebuilding a search index, or deleting catalog duplicates, will improve ranking KPIs.

1. **Treat the live index as the evaluated system.** A schema that already beats the baseline on aggregate Hit@1 can still lose the largest intent cohort. Do not recommend a rebuild from the aggregate win. Replay the losing cohort before cutover.
2. **A library upgrade is a coverage ceiling, not a ranking gain.** Count rows whose stored field would change, then count how many of those rows a retrieval clause or ranker reads. A fix on a tiny catalog fraction cannot close a multi-point Hit@1 gap alone. Reindexing with the same document builder cannot add columns the builder never writes; compare one live document with the source column before claiming the index has an alias.
3. **Store a field only if a consumer reads it.** A numeric field that is always zero, or a flag that is always false, is dead weight. Do not copy a signal that ranking already joins from a side store. Do not store a pure function of a code already on the document, such as province density from province code. Local density belongs in an offline probe until the ranker reads it.
4. **Recover nested links before rebuilding from the raw catalog.** If parent-child rows exist only in a missing enrichment file, export them from the live index first. The raw catalog often has no parent id. Dropping nested children regresses retrieval that matches child names.
5. **Separate redirect, field repair, and do-not-merge.**
   - Safe redirect: same normalized name, same house, same normalized street, and the same coordinate at about 1 m (5 decimal degrees). Redirect; do not hard-delete. Historical clicks may use the old id.
   - Name plus a ~11 m cell (4 decimal degrees) is a blocking key, not a merge. Different house numbers in that cell are distinct doors.
   - Same house, street, and ward inside that cell are tenants, units, or gates. Merging them destroys parent-child retrieval.
   - Hamlet or admin prefixes in the street column are a field repair, not a row delete. Do not null that street unless a hamlet field exists and the rural query path reads it; otherwise rural queries that match the street field lose recall.
   - Post-retrieval hygiene does not free candidate slots. Exclude inactive status and spam names at index time, but measure the slot count before calling it a Hit@1 fix.
   - String inequality of admin names overstates reform. Strip administrative prefixes before calling a province or ward change a merger. Anchor admin-token patterns; a bare substring matches real street names.
6. **Do not claim the refresh will raise Hit@1 until a paired replay.** Include the losing intent cohort and nested-child recall. Reject the rebuild if either falls.
7. **Answer accuracy and latency from the evaluated split, not from field gaps.** When asked whether an upgrade helps both, lead with the case artifact. Ceiling = `(current rank-1 hits + retrieval misses) / fixed denominator`. Split misses into selected ids absent from the catalog and the live index (probe with chunked `ids` queries; zero hits is a catalog gap), short ambiguous queries whose target is indexed (discrimination, not a missing field), and the residual field-shaped misses. Ranking failures already in the pool are not schema fixes unless a live ranker reads the new field. A head-keyword or top-query set is not a natural mix: do not use it to judge address or admin-reform gaps, and do not use a residential-heavy random sample to judge head-query fan-out.
8. **Latency that scales with candidate count argues against a wider mapping.** Do not treat parallel full-pipeline wall-clock as index latency; compare it with an isolated single-worker measurement before blaming the mapping. Bucket cases by retrieved candidate count and report Hit@1 beside latency. Extra n-grams, synonyms, or nested prefixes increase fan-out and move cases into the slow, low-Hit@1 bucket. A query that is already accurate, has zero retrieval misses, and is multi-second is query cost or contention, not a missing field. Prefer dropping unread clauses over adding fields.
9. **Separate a size cutoff from a malformed mandatory filter.** ASCII-fold the query against the indexed name and inspect the first request's actual filter clauses and hit count. If the folded name contains the query, the target is inside the first geo stage, and the request fills its size window, test a first-stage rescore or bounded fetch-depth change. For a one-token number-leading query, inspect the captured request body rather than selecting only pure-digit strings: slash-delimited and alphanumeric house numbers can dominate this cohort. Check whether the address builder substitutes the number for missing street text and then requires it to match `street_name`; a correct `street_number` cannot pass that filter, and rescore cannot resurrect it. Compare the selected document's street and house-number fields at both case and distinct-ID granularity; a local catalog may disagree with the captured index. Probe a general exact-number OR branch in the retrieval filter using the existing number normalizer, preserving the old street branch, status, target, geo, and size. Audit indexed field values and healthy cases before claiming recovery. For raw-hit pool misses, partition decoder rejection by status, target visibility, coordinates, and synthetic-name guard before attributing the residual to deduplication; compare captured status with the catalog by timestamp, never loosen status hygiene from catalog-only evidence. Category is a boost, not a filter, when a token has several plausible categories. Child-only ids need a child-field membership probe, not a schema redesign.
10. **Judge substitutes for absent ids without calling name overlap success.** Exact-id Hit@1 is zero when the id is missing from the catalog and the live index. A non-empty list is not a correct place. Split brand-generic queries, where a nearby same-brand result can be acceptable and production Hit@1 may already be near zero, from specific facilities, where production still shows the clicked id in the top 10. Report that production top-10 rate separately from the share of our rank-1 ids that also appear there. Gates and tenants whose names contain the facility query are not the clicked place.
11. **Confirm a missing id against the map pin before calling the place absent.** Open the map search at the query cluster. A result list often has no coordinates; open the place page and read `@lat,lon` from the URL. Scan the catalog within about 100 m for the same facility name. If that record exists under another id, the fix is an alias, not a new document or a new schema field. Do not use the user's search coordinate as the place pin.
12. **Queue near-substitutes; do not auto-relabel Hit@1.** A click can be the unhappy nearby POI. Require all of: the query names a facility and does not ask for a stall or gate; the focus is the click if it is in the catalog, otherwise rank-1; the focus is a stall (`tra da`, `quan tra`, `lotteria`, `kichi`) or, in a separate drop-off queue, a numbered gate (`cong 1`, `cong 2`, `cong vao`). Do not match bare `cong` — it matches `cong ty` and flags legitimate gate clicks. The parent must lie within 80 m, contain every facility head present in the query, and beat the tenant on token overlap. Take the best overlap, not the first grid hit; the first hit selects a club instead of the hospital. Keep pickup gates out of the defect queue. A Hit@1 whose clicked id differs from the shown gate id is an alias or displayed-id hit, not proof the user clicked the gate. Repeated rows of one pair are one place. Label a sample before quoting a rate, and do not change the ranker until more than one facility confirms the rule.
13. **Demote a co-located stall after scoring, inside the retrieved pool only.** Twin dedup does not see different titles a few tens of meters apart. ES score does not decide order when popularity sits inside the ranking score. Do not widen the dedup radius and do not cut popularity globally. After rank, if the query contains the facility heads and no stall marker, a stall within 80 m with worse query-token overlap must not outrank the best facility already in the pool. Leave numbered gates out. Aliasing a missing click id to the surviving facility does not fix Hit@1 if the stall still ranks above that id.
14. **Read the clicked stall's inputs before defining how users ask for it.** Aggregate `input_text` for that selected id across the permitted weekly logs. A stall token keeps the stall eligible to win; users do not need the full facility phrase. A facility-only query is facility intent. A short alias that contains neither the stall marker nor the facility head is a hole in a head-only demotion rule, not proof they searched for the stall. High trip count is pin use, not search-query evidence. If a cited source names an official expansion, add that phrase to the query-only acronym table so the query becomes the facility name. Do not add the acronym to a title-rewrite facility-alias map: that map rewrites every title containing the token, so the co-located stall becomes the facility name.
